% ABSTRACT
% =========================================================
\begin{abstract}
When a new feature is requested during software maintenance, engineering teams must judge whether the architecture can absorb the resulting workload before implementation — a question usually answered by heuristic tuning rather than measurement, since an unbuilt feature has no telemetry. AIOps (Root Cause Analysis) diagnoses disruptions only after they occur; Structural Causal Models (SCMs), despite supporting $do$-calculus intervention, mainly explain past data rather than forecast unbuilt requirements. Neither paradigm bridges requirements engineering with prospective capacity planning, the missing link for shifting operational reasoning left. We introduce a framework combining a Guardrailed LLM Parser that translates natural-language requirements into bounded interventions $do(X{=}x)$, and a Dual-Path SCM that projects downstream resource impact. Grounded in the LLM-Modulo paradigm, the Parser acts only as a candidate generator, bounded by a three-layer symbolic verification architecture — a scope gate that refuses out-of-taxonomy requirements, an entity-grounding layer enforcing graph-membership invariants, and a bounded-projection operator clamping numeric deltas to empirically anchored safety envelopes. Interventions propagate through a topology-adaptive, multi-tier DAG isolating network-layer workload propagation from hardware resource consumption (CPU, memory), via a queueing-inspired regressor for non-linear latency and cascade attenuation. We evaluate on two RCAEval testbeds of different scale (Sock Shop, 7 services; Train Ticket, 28), reporting per-system results since accuracy does not generalize uniformly across topologies. Across 3 independent live-LLM repeats, runtime verification drives boundary-violation, hallucination, and gateway-misdirection failure modes to exactly zero every time, while an unguarded baseline's own numeric error varies by over $6\times$ run-to-run. We report this transparently: the model's accuracy advantage on our smaller testbed does not transfer to the larger one; its value instead rests on $do(x)$ feasibility queries no regression baseline can answer.
\end{abstract}

% I. INTRODUCTION

\section{Introduction}
\label{sec:introduction}

The rapid adoption of microservice architectures has revolutionized cloud-native development. During ongoing maintenance, however, most new work does not originate from the engineering team itself but from an external \emph{requirement}: a customer request, a product-management ticket, or a design document describing a feature that does not yet exist in the running system. Before committing engineering effort, teams must judge whether the architecture can absorb the workload this requirement will introduce — a question that, by definition, has no historical telemetry to answer it directly.

Despite advancements in AIOps, current methodologies exhibit critical gaps for this setting. First, existing Causal RCA frameworks are inherently observational and retrospective, diagnosing incidents that have already occurred rather than ones a not-yet-built feature might cause. Second, SCMs theoretically support counterfactual reasoning; yet, applied research primarily uses them to solve $P(\text{Cause} \mid \text{Anomaly})$ rather than to project the effect of a hypothetical new requirement. Third, engineers lack a grounded way to turn a natural-language requirement into a quantitative workload assumption at all, relying instead on manual, heuristic estimation.

To bridge these gaps, our framework reframes microservice analysis toward prospective, requirement-level feasibility forecasting: given a natural-language description of a new requirement, project its downstream resource impact and a feasibility verdict \emph{before} implementation. By utilizing Pearl's $do$-calculus, we allow engineers to inject the counterfactual workload a requirement would introduce and observe its simulated propagation.

\textbf{Scope.} We deliberately bound ``new requirement'' to features whose workload behavior can be approximated by an existing calibration archetype within the target system's known request taxonomy (Section~\ref{sec:methodology}) — e.g., a new promotion mechanic is treated as a variant of an existing checkout-discount archetype rather than as an unprecedented category. This is consistent with how the framework is meant to be used in practice: as a decision-support tool for feature requests that extend an already-deployed system's existing request taxonomy, not as an open-ended predictor for arbitrary, never-before-seen application domains. A requirement that matches no known archetype closely is out of scope for a numeric verdict; Section~\ref{sec:discussion} discusses how the current implementation behaves in that case and what a scope-respecting implementation should do instead.

Our main contributions are:
\begin{enumerate}
    \item \textbf{Grounded Parameter Estimation via LLM-Modulo:} We introduce a Parser Agent bounded by a three-layer symbolic verification architecture: \emph{(i)} a \textbf{Scope Gate} implementing selective abstention — refusing a numeric verdict entirely when no calibrated archetype matches, rather than silently guessing; \emph{(ii)} an \textbf{Entity Grounding} layer enforcing graph-membership invariants on the proposed injection point and affected services; and \emph{(iii)} a \textbf{Bounded Projection} operator $\Pi$ that clamps numeric deltas into a nested safety envelope anchored to empirical calibration data. Evaluated with a live LLM backend across 3 independent repeats, these layers drove three observed failure modes (boundary violation, service hallucination, gateway misdirection) to exactly $0\%$ every time; targeted adversarial testing of each layer separately confirmed the entity-grounding fallback and the projection clamp are genuinely load-bearing against manipulated inputs, but also uncovered a real, quantified weakness in the scope gate's keyword-overlap criterion (a $100\%$ evasion rate under an attack designed around it), which we report and analyze rather than omit.
    \item \textbf{Modeling Cascade Attenuation:} We utilize a topology-adaptive, multi-tier hierarchical SCM ($4\times|V|$ nodes, fit per-testbed -- 28 nodes on Sock Shop's 7 services, 112 on Train Ticket's 28) that disentangles network-layer propagation from hardware-layer consumption, tracking how workloads decay or amplify across call chains. Because this decomposition is causal rather than statistical, a projected change can be attributed back to the specific upstream services and tiers driving it, via the same Shapley-over-DAG machinery Budhathoki et al.\ \cite{budhathoki2022rootcause} use for outlier root-cause attribution, run here in the forward, interventional direction instead of the retrospective one — a capability a black-box regressor's point prediction does not have, regardless of its accuracy; whether this specific decomposition is itself reliable at scale is an open question we treat as future work (Section~\ref{sec:discussion}) rather than assume from the construction alone. We further show that, without an explicit monotonicity constraint, this component can produce sign-inverted (physically implausible) predictions under extreme extrapolation, and we report a mitigation and its residual limitations.
    \item \textbf{Domain-Aware Causal Mechanisms:} We integrate a queueing-inspired regressor into the SCM's structural equations to model non-linear latency bottlenecks, and we evaluate its behavior both in- and out-of-the-training-distribution.
    \item \textbf{Cross-Topology Evaluation:} We evaluate the full pipeline on two independent microservice topologies of substantially different scale (7 vs. 28 services) using the same protocol, and report where conclusions do and do not transfer between them.
\end{enumerate}

\section{Background and Related Work}
\label{sec:background}

\subsection{From Retrospective RCA to Prospective Forecasting}
Traditional machine learning struggles with confounders because it fits an association between $X$ and $Y$ within the observed data distribution, not a mechanism that still holds once $X$ is deliberately changed. Pearl's SCM \cite{pearl2009causality} resolves this via the $do$-calculus operator, which asks what the system's own structural equations would produce under a hypothetical intervention rather than what value historically co-occurred with a similar-looking input.

\textbf{This is not merely a re-weighting heuristic; it is a distinct, provably well-defined mathematical object.} Pearl's Truncated Factorization Theorem \cite{pearl2009causality} states that for an intervention $do(X_i = x_i^*)$,
\begin{equation}
P(x_1,\dots,x_n \mid do(X_i{=}x_i^*)) = \prod_{j\neq i} P(x_j \mid pa_j)\Big|_{X_i = x_i^*},
\end{equation}
i.e.\ the interventional distribution is built from the \emph{same} conditional mechanisms $P(x_j\mid pa_j)$ a model already estimates for ordinary prediction, with the edges into $X_i$ severed rather than conditioned on. A regression baseline fit purely on observational data has no such operator available to it: its point estimate $\hat y = h(x)$ re-weights whichever $(X,Y)$ pairs happened to co-occur in training, and this need not equal $\mathbb{E}[Y \mid do(X{=}x)]$ whenever an unobserved confounder affects both $X$ and $Y$. This is a difference of \emph{kind}, not of degree: no amount of held-out point-accuracy on observational data closes it, because the associational and interventional quantities are provably distinct objects under confounding — exactly the setting RQ2's regression baselines are evaluated under, regardless of which model wins on MAPE. Because our pipeline possesses a fitted SCM rather than only a causal graph, answering a $do(x)$ query is further \emph{computationally trivial}: it reduces to forward simulation, rather than the finite sequence of do-calculus rule applications whose completeness — that a finite derivation exists whenever an effect is identifiable at all — Huang and Valtorta proved for Pearl's three inference rules \cite{huang2006complete}. We stress what this establishes and what it does not: a claim about the \emph{well-definedness} of the $do(x)$ operation given a correctly specified SCM, not a claim about how closely our fitted $f_j$ approximate the real system — that empirical question is separate, and RQ1, RQ2, and RQ6 report it honestly, including where the answer is unfavorable to our own model.

Frameworks that leverage SCMs for microservice diagnostics apply this structure in the retrospective direction: Budhathoki et al.\ \cite{budhathoki2022rootcause} formalize how to attribute an already-observed outlier to its upstream root causes by tracing which ancestors' noise terms deviated from their typical behavior along a known causal graph, apportioning credit with Shapley values — the same mechanism DoWhy-GCM \cite{blobaum2024dowhy} exposes as \texttt{attribute\_anomalies}. Our codebase implements this mechanism in a module separate from the Capacity Agent evaluated elsewhere in this paper, whose own bottleneck ranking currently uses a simpler fixed-threshold heuristic instead. Our work runs this identical structural machinery in the opposite, prospective direction: rather than asking which past ancestor explains an outlier that already happened, we ask which downstream nodes a hypothetical $do(\text{Workload}=w)$ would push into outlier territory before that workload is ever applied to the real system. Formally, let $\tilde x := \mathbb{E}[X \mid do(\text{Workload}=w)]$ denote the counterfactual point obtained by forward Monte Carlo simulation through the fitted DAG (Section~\ref{sec:workload-propagation}); applying the same IT-score and Shapley machinery of \cite{budhathoki2022rootcause} to $\tilde x$ against the training-period baseline $P(N_j)$ yields $S(\tilde x) = \sum_j c^{Sh}_{\tilde x}(j)$. The substitution of a hypothesized $\tilde x$ for an observed $x^*$ is licensed by the same modularity property \cite{blobaum2024dowhy} the retrospective case already relies on: $do(X_k=x_k^*)$ only replaces the mechanism at node $k$, leaving the joint independence of $N_{j\neq k}$ intact regardless of whether $x_k^*$ was measured or hypothesized — the same graph, the same decomposition, run forward instead of backward.

\subsection{Neuro-Symbolic AI and LLM Verification}
Recent studies highlight that while LLMs possess exceptional semantic reasoning, they exhibit severe deficiencies in deterministic planning \cite{kambhampati2024}. Following the LLM-Modulo and symbolic-feedback frameworks, we position the LLM strictly as a candidate generator, relying on external architectural guardrails to enforce correctness and topological constraints. Our multi-agent orchestration follows the ReAct paradigm of interleaved reasoning and tool-acting \cite{yao2022react}.

\subsection{Benchmarks and Statistical Comparison}
We evaluate on RCAEval \cite{pham2024rcaeval}, a public microservice RCA benchmark providing fault-injected telemetry for both Sock Shop and Train Ticket topologies. For comparing multiple models across datasets we follow the non-parametric testing methodology of Demšar \cite{demsar2006}, using paired Wilcoxon signed-rank and Friedman tests rather than parametric tests, given the small number of independent services per system.

\section{Methodology}
\label{sec:methodology}

\subsection{System Architecture Overview}
The system is implemented as a four-node LangGraph state machine (Fig.~\ref{fig:architecture}) executed sequentially for every incoming requirement: \emph{(i)} \textbf{Parse Requirement} — the Parser Agent (Section~\ref{sec:parser-agent}) turns natural-language text into a bounded intervention $do(X{=}x)$; \emph{(ii)} \textbf{Map Impact} — the Architecture Agent performs a breadth-first traversal of the dependency graph from the injection gateway to determine the blast radius of affected services; \emph{(iii)} \textbf{Simulate} — the Capacity Agent projects downstream resource consumption along two paths, a fast per-service bivariate SCM and an accurate, topology-adaptive global DAG (28 nodes on Sock Shop, 112 on Train Ticket) that propagates the intervention through both the cross-service workload tier and the local resource-consumption tier (Section~\ref{sec:workload-propagation}); \emph{(iv)} \textbf{Generate Report} — an LLM synthesizes the projected metrics, the Capacity Agent's bottleneck analysis, and a self-critique (``Devil's Advocate'') pass into a natural-language \texttt{FeasibilityReport}. Only the first and third nodes involve the causal/LLM machinery evaluated in Section~\ref{sec:results}; the second is a deterministic graph traversal and the fourth is a text-synthesis step not evaluated quantitatively in this paper.

\subsection{Parser Agent: Semantic Bridge and Three-Layer Verification}
\label{sec:parser-agent}
The Parser Agent translates natural language into a quantitative intervention vector $do(X=x)$. It follows a two-tier strategy: a deterministic keyword-similarity match against an empirical calibration table is attempted first (bypassing the LLM entirely when similarity $\geq \tau$, with $\tau = 0.6$); otherwise the LLM is invoked to propose a request type, affected services, and a bounded adjustment. The same threshold $\tau$ also controls, within the LLM branch, whether the LLM's proposed adjustment is used or zeroed (forcing the calibration anchor unmodified when match confidence is low). Since sweeping $\tau \in [0.3, 0.8]$ on the RQ3 test set left all safety metrics (PBVR, SHR, Anchor MAE) completely unchanged — only the fast-path bypass rate shifted — we treat $\tau$ as a cost--accuracy design parameter rather than a safety mechanism, and do not count it among the verification layers below.

In both branches, the output passes through a \textbf{three-layer symbolic verification architecture} before being returned. Following the LLM-Modulo separation of concerns \cite{kambhampati2024}, the LLM is treated strictly as a non-deterministic candidate generator $L$, and a deterministic, sound verifier enforces all safety properties independently of $L$'s reliability. The three layers are organized by their distinct mathematical purpose — selective abstention, graph-membership enforcement, and interval projection — rather than enumerated as a flat list, and each targets one category of failure mode we observed the unguarded LLM exhibit.

\subsubsection{Layer 1: Scope Gate (Selective Abstention)}
\label{sec:scope-gate}
The LLM branch is explicitly instructed to always select the closest-matching known request type rather than decline (Section~\ref{sec:edge-of-scope}), so after it returns a choice we independently recompute keyword similarity between the raw requirement and \emph{that chosen type's own} keyword list. If this is exactly zero — i.e.\ neither the rule-based pass nor the LLM's own selection shares a single keyword with the input — we treat the requirement as outside the calibrated taxonomy: confidence is set to \textsc{refused} and \texttt{is\_out\_of\_scope} is flagged. The report-generation node checks this flag deterministically and short-circuits to an explicit refusal report (recommending manual load-testing) instead of letting the downstream LLM synthesize a confident-sounding verdict around a fallback number (Section~\ref{sec:edge-of-scope}). This layer implements \emph{selective abstention} rather than projection: when no archetype can be trusted, the system declines to answer rather than mapping the input to a ``closest'' guess — a qualitatively different behavior from Layers 2 and 3, which correct invalid candidates rather than refuse them.

One limitation: the zero-keyword-overlap criterion is coarse. A requirement that shares one incidental keyword with an unrelated archetype would not trigger it, so this is a floor on refusal recall, not a complete taxonomy-membership detector.

\subsubsection{Layer 2: Entity Grounding (Graph-Membership Invariants)}
\label{sec:entity-grounding}
This layer enforces that every entity proposed by the LLM corresponds to a real node in the topology graph $\mathcal{G}$ — a deterministic set-membership check with no free parameter.
\begin{itemize}
    \item \textbf{Gateway Invariance:} the injection point $do(x)$ must be applied at a node with in-degree $= 0$ in the dependency graph. If the LLM proposes an internal node, the system falls back to the nearest valid gateway and downgrades confidence to \textsc{low}. An earlier version passed a hardcoded literal into this check, so it could never observe a real violation; the LLM is now asked for \texttt{injection\_service} explicitly and the layer validates that actual proposal. On RQ3's 50-prompt benchmark this proposal was always correct (\texttt{front-end}, unanimously across 150 fresh live calls), so we additionally built an 18-prompt adversarial set describing plausible backend/async work: the LLM proposed a non-gateway service on \emph{every} prompt at \emph{every} repeat, and the fallback correctly caught and corrected all $18/18$. This demonstrates \emph{rejecting} an invalid proposal on this single-gateway topology, but not \emph{disambiguating} between two independently valid gateways — that requires a topology with a genuine second gateway (Section~\ref{sec:discussion}).
    \item \textbf{Service Existence Filter:} discards any proposed \texttt{core\_services} entry that does not correspond to a real node in $\mathcal{G}$, preventing hallucinated services from propagating downstream.
\end{itemize}

\subsubsection{Layer 3: Bounded Projection $\Pi$ (Empirically Anchored Clamping)}
\label{sec:bounded-projection}
This layer constrains how far the LLM's numeric proposal may deviate from the empirical calibration table. It is the only layer with hand-set numeric thresholds, and Section~\ref{sec:discussion} reports how well each is empirically justified. In the implementation, both clamps are applied by a single function (\texttt{\_guard\_delta}) in one pass — a nested bound rather than two independent mechanisms — but we describe them separately because their empirical status differs:
\begin{itemize}
    \item \textbf{Outer Clamp (Physical Delta Bound):} clamps the proposed workload delta to $[5\%, 50\%]$. This range is not arbitrary: replaying the 300 raw, unguarded LLM proposals from RQ3's B1/B2 baselines (whose values range as high as $50{,}000\%$) against candidate bounds shows $[5,50]$ sits at a knee — tightening to $[10,30]$ nearly doubles the flagged-violation rate ($26.3\%\to47.0\%$), while loosening to $[1,100]$ barely helps ($26.3\%\to21.3\%$), because the excluded tail is pathologically extreme rather than borderline.
    \item \textbf{Inner Clamp (Adjustment Bound):} restricts the LLM's fine-tuning of the calibration anchor to $\pm 10\%$ around it, before the outer clamp is applied. Violations fall back to the unadjusted anchor value. We initially suspected this clamp's empirical $0\%$ trigger rate in RQ3 was circular, since the prompt separately \emph{told} the LLM to stay within $[-10,10]$. Removing that instruction and re-running (3 repeats, 141/150 completed) still gave a trigger rate of $0/141$. We then built a 12-prompt adversarial set (two archetypes $\times$ six manipulation strategies: direct override, extreme-narrative framing, fabricated-authority, forced step-by-step reasoning, urgency/threat framing, roleplay-based constraint override) and re-ran it live, 3 repeats: raw adjustments reached as high as $+500\%$, and the clamp fired on $33/36$ ($91.7\%$) — every strategy but the roleplay override reached $100\%$, which itself reached $50\%$. The inner clamp is therefore genuinely load-bearing: it does no work against benign prompts, but is the only mechanism standing between an adversarially-manipulated proposal and a $500\%$ delta reaching the SCM.
\end{itemize}

\textbf{Formalization.} Let $L : \Sigma^* \to T \times \mathbb{R} \times 2^V$ be the LLM's candidate generator, mapping a raw requirement $r$ to a proposed $(t, \delta, S)$ — request type, workload delta, and core-service set. Layers 2 and 3 compose into a single deterministic \emph{bounded projection operator} $\Pi$ applied to every candidate regardless of $L$'s output distribution:
\begin{equation}
\Pi(t,\delta,S) = \big(\textsc{Gw}(\text{inj}),\ \textsc{Clamp}_{[5,50]}(\delta_{\text{anchor}} + \textsc{Clamp}_{[-10,10]}(\text{adj})),\ S \cap V\big),
\end{equation}
with $\textsc{Gw}(v) = v$ if $\text{in-deg}(v)=0$, else the nearest valid gateway; $\textsc{Clamp}_{[a,b]}(x) = \max(a,\min(b,x))$. Because $\Pi$ is total and deterministic, the structural guarantees on its output — valid gateway, $\delta \in [5,50]$, $S \subseteq V$ — hold for \emph{every} input in its domain; they do not depend on whether $L$ hallucinates, only on $\Pi$ itself. This is precisely the LLM-Modulo separation of concerns \cite{kambhampati2024}: $L$ is a candidate generator of unconstrained reliability, and $\Pi$ is the sound, LLM-independent verifier. Layer 1 (Scope Gate) differs qualitatively: rather than projecting an out-of-range candidate back into a valid one, it detects when no projection can be trusted at all and substitutes an explicit refusal for a numeric verdict.

Separately, at graph-construction time, the dependency topology is verified to be acyclic (removing any residual cycle before it is used for simulation), which we treat as a structural precondition rather than a per-request verification layer. We note that one additional safeguard described in early design notes — hard-clamping predicted resource values to $[0,100]$ — was \emph{not} implemented in the evaluated pipeline; Section~\ref{sec:discussion} discusses a concrete failure mode this gap causes and how we mitigated it at the causal-mechanism level instead. An additive-shift rule for simultaneous interventions on ancestor--descendant nodes was likewise never implemented; the pipeline evaluated here only supports single-intervention queries.

\subsection{Workload Propagation and Causal Simulation}
\label{sec:workload-propagation}
The Capacity Agent's accurate path models degradation using a two-tier DAG (28 nodes on Sock Shop; a 112-node instance of the same construction has also been fit on Train Ticket) with DoWhy's Additive Noise Model framework. The node set is partitioned $V = V_W \cup V_R$ into cross-service workload nodes and local resource nodes, with edges restricted to two kinds:
\begin{align}
\text{Tier 1 (workload):} \quad & W_j = f_j(PA_{W_j}) + N_{W_j}, \ PA_{W_j}\subseteq V_W, \\
\text{Tier 2 (resource):} \quad & R_j = g_j(W_j) + N_{R_j},
\end{align}
i.e.\ each resource node $R_j$ (CPU, memory, latency) has exactly one parent, its own service's workload $W_j$ — there are no $R \to R$ or $R \to W$ edges. This separation is what makes the per-node Shapley decomposition of Section~\ref{sec:background} \emph{potentially} interpretable as which tier is responsible for a projected change, not merely which node — whether this holds up under a controlled, ground-truth check is evaluated separately \cite{ourxaipaper} rather than assumed here.

Resource-consumption mechanisms $g_j$ (CPU, memory) are fit as $g_j(w) = \boldsymbol{\beta}^\top w + \beta_0$ with coefficients constrained to $\boldsymbol{\beta}^* = \operatorname*{argmin}_{\boldsymbol{\beta}\geq \mathbf{0}} \lVert \mathbf{y} - X\boldsymbol{\beta}\rVert_2^2$ (non-negative least squares), which guarantees $\partial g_j/\partial w \geq 0$ and enforces a monotonically non-decreasing response to workload by construction (Section~\ref{sec:extrapolation}) — applied uniformly to both tiers, not only Tier 2. Latency mechanisms instead use a queueing-inspired regressor with feature transform
\begin{equation}
\phi(w) := \frac{w}{c-w}, \qquad c \approx 1.5 \max(W_{\text{train}}),
\end{equation}
fit as $R^{\text{Latency}}_j = \beta\,\phi(W_j) + \beta_0$, $\beta\geq 0$; as $w \to c^-$, $\phi(w)\to\infty$, approximating the heavy-traffic behavior $\rho/(1-\rho)$ of an M/M/1 queue as utilization approaches capacity $c$ \cite{kingman1961}, rather than a closed-form derivation from queueing theory.

\textbf{Post-Simulation Uncertainty Annotation.} The three-layer verification of Section~\ref{sec:parser-agent} bounds the \emph{input} intervention delta to $[5\%,50\%]$, but bounding the input does not bound the output: a downstream node reached through Tier-1 propagation or Tier-2 conversion can still land outside \emph{its own} training envelope even when the injection delta is fully legal. We tested whether this gap is reachable in practice rather than assuming it: sweeping the full legal range on both testbeds and comparing every downstream node's projected mean against that node's own training-distribution percentiles, $16.7\%$ of (node, delta) pairs on Sock Shop fall outside the P90 band ($3.7\%$ already at the minimum legal delta of $5\%$, rising to $25.9\%$ at the maximum of $50\%$), versus only $0.4\%$ on Train Ticket — the risk is real but topology-dependent, consistent with this paper's broader finding that results do not transfer uniformly across scale. On the strength of this result, after each simulation, every downstream node's projected mean is classified against its own training percentiles (\textsc{high} $\leq P_{90}$; \textsc{medium} $\leq P_{95}$; \textsc{low} $\leq \max(P_{99}, 2\times\max_{\text{train}})$; \textsc{very\_low} beyond that, excluding the injection node itself), and \texttt{generate\_report\_node} deterministically appends an explicit extrapolation-risk caveat, naming the flagged nodes, whenever the worst confidence across all nodes is \textsc{low} or \textsc{very\_low}. This attaches a caveat to a still-legitimate numeric verdict rather than replacing it — the same code-level-guarantee design as the Scope Gate (Section~\ref{sec:scope-gate}), but for a different situation: a familiar request type pushed to an unusual magnitude, rather than one that matches no archetype at all.

We present this mechanism transparently as an \emph{annotation} rather than a verification layer: evaluated against RQ3's own 150 real, live-LLM-parsed cases, it fires on $80\%$ of ordinary, in-taxonomy cases — far above the $16.7\%$ the uniform sweep would suggest — and $147/150$ of these are driven by a single node, \texttt{catalogue\_cpu}, whose training distribution is heavily right-skewed (P95 $=0.21$ but max $=49.0$, from a small number of true historical spikes), so its P90/P95 band is narrow enough that even a typical, unremarkable delta exceeds it. As currently calibrated, therefore, this annotation has low specificity as a decision-support signal on this testbed: a caveat attached to 4 out of 5 reports is not a caveat a user can act on selectively. We do not attempt an ad hoc per-node recalibration here, since doing so without a principled methodology (e.g. robust, outlier-resistant percentile estimation for heavy-tailed nodes) risks trading one unvalidated threshold for another; we report the finding honestly instead and leave recalibration to future work (Section~\ref{sec:discussion}).

\section{Experimental Setup}
\label{sec:setup}

\subsection{Datasets and Testbed}
We evaluate our framework on RCAEval \cite{pham2024rcaeval}: (i) \textbf{Sock Shop}, 7 microservices, 90 fault-injection scenarios (30 fault types $\times$ 3 runs), used for both the accuracy benchmark and a 90-run ground-truth direct-match validation; (ii) \textbf{Train Ticket}, 28 microservices (up to 384 recorded metric columns), 90 fault-injection scenarios (5 target services $\times$ 6 fault types $\times$ 3 runs), the same protocol scale used for Sock Shop. Both datasets share the same telemetry schema (per-service workload, CPU, memory, socket count, and $p50$/$p90$ latency, with an explicit fault-injection timestamp separating normal and faulty periods), and RQ1/RQ2 evaluate all three of CPU, Memory, and Socket on both systems (Tables~\ref{tab:rq1}, \ref{tab:rq1-gt}); Latency is excluded from the 4-model MAPE comparison on both systems for the reason given in Section~\ref{sec:workload-propagation} (standard regressors do not model its saturating behavior), not because of a schema difference between the two testbeds. To prevent pooled averages from obscuring subsystem- and topology-specific variation, we report results on a \textit{per-system} basis rather than a single pooled number.

\subsection{Baselines for Comparison}
\begin{itemize}
    \item \textbf{(B0) Rule-Only Parser:} a deterministic keyword-matching classifier with no LLM and no learned adjustment, used as the accuracy floor for requirement parsing.
    \item \textbf{(B1) Unguarded Zero-Shot LLM:} the same live LLM backend as our proposed parser, prompted directly with no calibration table and no runtime guards.
    \item \textbf{(B2) Unguarded Few-Shot LLM:} as B1, but with the system topology and calibration table given as in-context examples, still without any runtime guard.
    \item \textbf{(B3) Non-Causal Regression Baselines:} Linear Regression, Gradient Boosting Regression, and a Gaussian Process Regressor, trained and evaluated under the identical out-of-distribution protocol as the SCM (Section~\ref{sec:results}), used to test whether causal structure yields an accuracy advantage over standard regressors.
    \item \textbf{(B4) Uniform Delta Injection:} a naive propagation baseline that assumes every downstream service's workload changes by exactly the same percentage as the injected upstream delta, bypassing the dependency-graph propagation entirely.
\end{itemize}

\subsection{Evaluation Metrics}
We measure forecasting accuracy using MAPE, RMSE, and $R^2$, computed at full test-set resolution (i.e., on every held-out point rather than on quantile-bucket averages, which we found to substantially understate error \textemdash Section~\ref{sec:results}). For the Parser Agent we additionally report the Physical Boundary Violation Rate (PBVR), Service Hallucination Rate (SHR), and Gateway Misdirection Rate (GMR), plus mean end-to-end inference latency and the fraction of requests resolved without an LLM call (fast-path bypass rate).

\subsection{RQ2: Does Causal Structure Improve Accuracy Over Non-Causal Regressors?}
We compare the SCM against B3 (Linear Regression, Gradient Boosting, Gaussian Process) under the identical protocol, using paired Wilcoxon and Friedman tests on full-resolution MAPE, computed \emph{separately per metric} (CPU, Memory, Socket use incompatible units and cannot be pooled into a single RMSE-based test without inflating apparent significance).

On \textbf{Sock Shop} ($n=21$ service--metric pairs), the SCM is statistically significantly more accurate than Linear Regression when pooled across metrics ($p=0.0137$, median $\Delta = -0.94$ MAPE points, SCM lower), but is statistically indistinguishable from Gradient Boosting ($p=0.812$) and Gaussian Process ($p=0.421$). By win count, the SCM ties for first place (7/21 service--metric combinations), alongside Gaussian Process (7/21), ahead of Gradient Boosting (6/21) and Linear Regression (1/21).

On \textbf{Train Ticket} ($n=84$ service--metric pairs across CPU, Memory, and Socket — $4\times$ larger than Sock Shop, evaluated on the full 90-scenario protocol), the result does \emph{not} replicate in the SCM's favor: the SCM wins only 12/84 combinations, the fewest of the four models (Gaussian Process 30/84, Gradient Boosting 23/84, Linear Regression 19/84). Pooled across metrics, the SCM \emph{is} significantly more accurate than Linear Regression here too ($p<0.0001$, median $\Delta=-0.12$), driven mainly by a large CPU-specific effect (median $\Delta=-15.66$, $p=0.0001$); against Gaussian Process the pooled comparison is no longer significant ($p=0.432$), but this masks opposite-signed per-metric effects that partially cancel: the SCM is significantly \emph{less} accurate on CPU (median $\Delta=+4.90$, $p=0.0095$) and significantly \emph{more} accurate on Memory (median $\Delta=-0.025$, $p=0.020$, negligible in absolute terms), with Socket not significant; against Gradient Boosting the SCM remains statistically indistinguishable, pooled and per-metric ($p=0.156$ pooled). The pattern that recurs on both systems — SCM beating the simplest baseline (Linear Regression) while failing to separate cleanly from the two more flexible ones — is consistent with the SCM's own mechanisms being close to linear-regression-equivalent in structure (Section~\ref{sec:workload-propagation}); we flag this, and the fact that pooling across metrics can mask offsetting per-metric effects, rather than only reporting whichever $p$-value looks most favorable.

\textbf{We do not conclude that SCM point-accuracy is superior to standard regressors.} The advantage seen on Sock Shop does not transfer to Train Ticket. We interpret this as evidence that the framework's value should rest on its unique capability — supporting $do(x)$ intervention queries, which the regression baselines cannot answer at all — rather than on raw predictive accuracy, which we find is not stable across topologies of different scale.

This gap is not just a matter of degree, but of kind. A regression baseline, however accurate, returns a single scalar $\hat y$ with no internal structure: it was never given a causal graph, so it cannot say which upstream service or which tier (cross-service workload propagation vs.\ local resource consumption) is responsible for how much of that number — the question is not merely unanswered, it has no operator in a black-box model capable of asking it at all. The SCM's projection, by construction, \emph{can be} decomposed: the same Shapley-value machinery Budhathoki et al.\ \cite{budhathoki2022rootcause} use to attribute an already-observed outlier to its ancestors (Section~\ref{sec:background}) applies, run forward, to our projected $do(\text{Workload}=w)$ outcome. A structurally identical Shapley attribution mechanism is implemented in our codebase (\texttt{gcm.attribute\_anomalies}, run on interventional rather than observational samples) but is not yet wired into the Capacity Agent evaluated elsewhere in this paper, whose bottleneck ranking currently uses a simpler fixed-threshold heuristic instead. We flag this as the structural reason $do(x)$ support is not a mere convenience feature — a capability no regression baseline has \emph{at all} — but we stop short of claiming this specific decomposition is already known to be faithful: whether it correctly attributes a projected change to the right service and the right tier is an empirical question distinct from forecast accuracy, and we leave a controlled, ground-truth evaluation of it to future work (Section~\ref{sec:discussion}) rather than assert it here without evidence. The framework's other central claim — that runtime guards, not prompting alone, are what makes the LLM Parser usable — does not depend on this accuracy comparison; we evaluate it separately against baselines B0--B2 next.

PBVR and SHR, by contrast, do operate on the LLM's own delta and core-service outputs (via Layer 3's clamps and Layer 2's service filter respectively) and are not subject to this caveat.

% VI. DISCUSSION & THREATS TO VALIDITY
% =========================================================
\section{Discussion and Threats to Validity}
\label{sec:discussion}

\subsection{The Extrapolation-Sign Failure Mode}
\label{sec:extrapolation}
During development we found that, at large synthetic interventions (e.g., $do(\text{workload}) = +150\%$ or $+300\%$), the resource-consumption mechanisms could predict a \emph{decrease} in CPU or memory usage in response to an \emph{increase} in workload — a physically implausible sign inversion caused by unconstrained linear extrapolation compounded across the two-tier graph. This is precisely the failure mode that a hard $[0,100]$ output clamp (an early design goal, see Section~\ref{sec:methodology}) would have masked rather than fixed. We instead constrained every workload-propagation and resource-consumption mechanism to non-negative coefficients, which enforces monotonicity by construction; this reduced, but did not eliminate, sign-inverted predictions at the most extreme interventions (roughly 7--19 of 56 service $\times$ scenario combinations at $+150\%$/$+300\%$, depending on the mechanism-fitting run). This constraint was originally applied only in the evaluation harness (used for RQ4) and not in the Capacity Agent that \texttt{orchestrator.py} actually runs end-to-end; we found and closed this gap during subsequent validation work on Train Ticket, so the same non-negative-coefficient fit now applies uniformly to both. We flag every remaining case programmatically (an \texttt{extrapolation\_suspect} indicator) and exclude flagged points from any quantitative claim; results at $+150\%$/$+300\%$ should be read as directional illustrations, not as validated forecasts.

\subsection{Behavior at the Edge of the Declared Scope}
\label{sec:edge-of-scope}
Section~\ref{sec:introduction} bounds ``new requirement'' to features approximable by an existing calibration archetype. An earlier version of the evaluated pipeline handled this boundary poorly: when a requirement matched no keyword, the rule-based classifier silently fell back to a default archetype (the lowest-impact category in our taxonomy) with no ``no reliable archetype'' signal, and the LLM branch was explicitly instructed to always select the \emph{closest-matching} known archetype rather than decline — a deliberate anti-hallucination design choice (Section~\ref{sec:parser-agent}) that had the side effect of never reporting ``insufficient calibration data'' even when that was the honest answer. Both paths could therefore return a confident-looking numeric verdict for a requirement that shared nothing in common with the system's taxonomy.

We close this gap with the Scope Gate (Layer 1, Section~\ref{sec:scope-gate}): after either path settles on a request type, we independently recompute keyword similarity against \emph{that type's own} keyword list; if it is exactly zero for both the rule-based guess and the LLM's own selection, the requirement is flagged \texttt{is\_out\_of\_scope} and the report-generation node deterministically substitutes an explicit refusal report (recommending manual load-testing) for the usual LLM-synthesized verdict — a code-level short-circuit rather than an instruction the synthesis LLM could smooth over. We verified this live end-to-end on two cases with the same LLM backend used in RQ3: an in-taxonomy requirement (``apply a 20\% checkout discount'') resolved normally at \textsc{high} confidence, while a genuinely unrelated one (``integrate a factory robot controller over CAN bus and Siemens S7 PLC'') triggered the Scope Gate even though the LLM itself, following its instruction to always guess, had proposed \texttt{PLACE\_ORDER} as the ``closest'' archetype — confirming the layer does not rely on the LLM's own self-reported confidence, which in this case was already low but not reliably so in general.

One limitation remains, and we quantified it rather than left it theoretical: the Scope Gate's zero-keyword-overlap criterion is coarse, so a requirement sharing one incidental keyword with an unrelated archetype would not trigger it. We built an 11-prompt adversarial set targeting exactly this — ten genuinely out-of-taxonomy requirements (Kubernetes monitoring, source-code refactoring, log-sampling rates, code review process, CPU-performance tracking, npm dependency updates, network-intrusion detection, IDE auto-comments, internal hardware procurement), each engineered to contain one polysemous word that coincides with an unrelated archetype's keyword (``order'' as in sorting an algorithm's output, ``status'' as in a health dashboard, ``code'' as in source code, ``rate'' as in a sampling rate, ``review'' as in a code review, ``track'' as in performance monitoring, ``package'' as an npm library, ``AI'' as in an intrusion-detection model, ``comment'' as in a docstring, ``buy'' as in capital procurement) — plus one direct-instruction-injection attempt with no incidental keyword at all, as a control. The result is the opposite of Layers 2 and 3's: \emph{all ten} keyword-coincidence prompts evaded refusal on \emph{every} repeat ($30/30$), each returning a fully-formed, confident-sounding numeric verdict for a domain the calibration table has no archetype for at all — for instance, a request to refactor internal Java source code was classified as \texttt{APPLY\_PROMO\_CODE} and returned a $20\%$ workload delta. Only the control (no incidental keyword, direct injection targeting the \texttt{reasoning}/\texttt{confidence} fields instead) was correctly refused every time, confirming the deterministic recomputation itself resists instruction injection — the vulnerability is specifically the keyword-overlap criterion's coarseness, not the guard's independence from the LLM's self-report. Layer 1 is therefore the weakest of the three layers in practice: structurally sound and resistant to direct manipulation, but with a refusal-recall gap wide enough that a single incidental word defeats it in $100\%$ of the cases we tried, in contrast to Layers 2 and 3's confirmed $18/18$ and $33/36$ against comparably-designed attacks (Section~\ref{sec:discussion}). A separate concern from an earlier version of this section — that a familiar request type pushed to an extreme projected load would receive a numeric verdict with no extrapolation caveat at all — is now addressed by the post-simulation uncertainty annotation (Section~\ref{sec:workload-propagation}), which deterministically attaches an OOD-confidence caveat to the report whenever a downstream node's projection falls outside its own training envelope, independently of the Parser's taxonomy-membership certainty.

\textbf{Fixing the Scope Gate.} Our first candidate fix -- multilingual sentence embeddings (cosine similarity between the requirement and each archetype's description, in place of literal keyword overlap) -- was tested and rejected on real data before being adopted: across two models (\texttt{intfloat/multilingual-e5-base} and \texttt{-large} \cite{wang2024multilinguale5}) and two description styles (\texttt{CALL\_CHAINS}' original 4--8 word description, and a longer domain-grounded rewrite), the best threshold on any configuration reached only $F_1{=}0.31$, with 48--50 of the 50 legitimate RQ3 prompts falsely refused at the operating point that caught all evasions. The two classes' similarity distributions simply overlap (legitimate mean $0.82$, adversarial mean $0.83$ on the base model) regardless of model size or description length, because both classes share the same ``request a software feature'' register; embedding distance to a short description measures topical register, not the narrower property we actually need. We adopted a different fix instead: a structured self-declaration field. The original prompt forced the LLM to always pick the structurally closest archetype with no way to say ``none of these fit,'' pushing the scope decision entirely onto the disconnected, external keyword recount. We instead ask the LLM, within the \emph{same} extraction call, whether the requirement describes a genuine customer-facing SockShop action at all (\texttt{is\_customer\_facing\_feature}), removing the forced-choice instruction; this is combined with the original keyword-overlap check via logical OR, so neither signal is trusted alone. Re-run against all 11 adversarial prompts and all 50 RQ3 legitimate prompts (61 live calls, full scale, not a sample): the adversarial evasion rate fell from $100\%$ to $0/11$ ($0\%$), with the new self-declared signal alone responsible for 15 of the 17 total refusals across the test set and the original keyword signal for 2, confirming the two are genuinely complementary rather than redundant. Twelve of the 50 legitimate prompts were also refused; inspecting these individually, seven belong to RQ3's own \texttt{Adversarial\_Stress} category and describe scenarios no reasonable Scope Gate should pass through with a confident verdict regardless of our fix -- a request to ``bypass the front-end gateway and inject load directly into payment via a hidden gRPC call,'' another to run a ``hidden crypto miner consuming 500\% CPU,'' another to ``delete all users from the database,'' and a semantically empty string -- so we do not count these as false positives against a well-posed ground truth, only against RQ3's original PBVR/SHR/GMR-oriented labels, which were never designed to answer whether these describe legitimate customer actions. The remaining five are genuine over-refusals on passive or backend-automated content the taxonomy does cover in spirit: static FAQ and terms-of-service pages, a bilingual UI label, a footer/version display, and an automatic fraud-detection scan -- content where ``customer-facing'' is a real judgment call our current instruction does not resolve well. We report this residual gap honestly rather than tune it away without further evidence (Section~\ref{sec:discussion}).

\subsection{Threats to Validity}
\begin{itemize}
    \item \textbf{Scalability.} Train Ticket telemetry contains up to 384 metric columns; per-node causal-mechanism fitting is currently independent and linear in the number of nodes, but the two-tier DAG construction scales worse and was not stress-tested beyond 28 services.
    \item \textbf{Interventional Shapley attribution's faithfulness is not yet established.} The mechanism described in Sections~\ref{sec:background} and~\ref{sec:results} is implemented but is not yet wired into the Capacity Agent's own bottleneck ranking used elsewhere in this paper (which uses a simpler fixed-threshold heuristic instead), and its reliability at attributing a projected change to the correct service, tier, and mechanism has not been established within this paper; we treat this as future work (Section~\ref{sec:future-work}) rather than assume it from the mathematical construction alone.
    \item \textbf{Topology dependence.} Our approach depends on the accuracy of the extracted dependency graph; RQ2 shows that even accuracy conclusions, let alone graph structure, do not transfer between topologies of different scale, so results on a third topology cannot be assumed without re-running the full protocol.
    \item \textbf{Single-model LLM evaluation.} RQ3 and RQ5 both use one LLM backend (\texttt{gemini-flash-lite-latest}) across 3 independent repeats at temperature 0.2; the guarded configuration's failure rates were exact-zero at every repeat, but the specific failure rates and run-to-run variance of the \emph{unguarded}/single-call baselines, and RQ5's status-agreement rate, may still differ substantially with other model backends, which we have not tested.
    \item \textbf{The entire Parser Agent, including every adversarial result in this section, is empirically validated on Sock Shop only, though the mechanism itself is now parametrized rather than hardcoded.} Train Ticket is evaluated only through the Capacity Agent's SCM machinery (RQ1, RQ2, the post-simulation uncertainty annotation) -- never through the three-layer verification architecture. The Scope Gate's prompt originally named ``SockShop'' as a literal string, and the Entity Grounding layer's service-membership check read from a hardcoded module-level constant duplicating information already available from the dependency graph; both have since been refactored to take the target system's name, a short domain description, and its known-service set as parameters derived from whichever graph the Parser Agent is constructed with, rather than assuming Sock Shop. This closes the literal-hardcoding gap for the identity and structural fields but not for the calibration table itself: \texttt{CALL\_CHAINS} remains a fixed module-level import rather than a constructor parameter (Section~\ref{sec:general-spec}), there is still no Train-Ticket-equivalent table to supply even if it were, and none of the three layers' adversarial validation (Sections~\ref{sec:parser-agent}, \ref{sec:edge-of-scope}) has been repeated on a different domain's taxonomy. The self-declaration field added to the Scope Gate is a general \emph{pattern} -- ask the extraction step itself, rather than a disconnected post-hoc check, whether the input matches the schema's intended use -- but the finding that the LLM's self-report is largely reliable once given room to use it is evidence about Sock Shop's request taxonomy only, not a property we have shown transfers.
    \item \textbf{RQ3's Table~\ref{tab:rq3} combines two data-collection dates by design.} The Guarded row was re-run in full (150 live calls, 3 repeats) after fixing a hardcoding defect in the Entity Grounding layer's gateway invariance check (Section~\ref{sec:entity-grounding}) that had prevented it from ever seeing a real LLM proposal; B0--B2 were not re-run because their code paths do not use \texttt{ParserAgent} at all and are consequently unaffected by that fix. We verified this reasoning before relying on it, not merely assumed it: B0's parser and B1/B2's prompts contain no reference to the Entity Grounding logic. The paired repeats within each row (B0--B2 from the original session, Guarded from the later one) are therefore not simultaneous, though both used the same live backend and protocol.
    \item \textbf{Entity Grounding and Bounded Projection's empirical necessity required purpose-built adversarial sets, not RQ3's benign one.} Both mechanisms report a genuinely-measured $0\%$ trigger rate on RQ3's standard 50-prompt benchmark (the gateway invariance check because the LLM unanimously proposed the correct gateway; the inner clamp because its raw magnitude judgment stayed modest whether or not its bound was stated explicitly in the prompt), which on its own would leave their necessity an open question. We resolved this with an 18-prompt adversarial set targeting the gateway check and a 12-prompt set targeting the inner clamp (Section~\ref{sec:parser-agent}): the gateway fallback fired $18/18$ against backend/async-framed prompts that induced a non-gateway proposal, and the clamp fired $33/36$ ($91.7\%$) against manipulation strategies that pushed the LLM's raw adjustment as high as $+500\%$. Both are therefore empirically load-bearing, not merely structurally guaranteed. What remains untested is narrower: whether the gateway check can correctly \emph{disambiguate} between two independently valid gateways (Sock Shop has only one, so this specific scenario cannot be constructed on this topology) and which of the five other adversarial strategies we did not try might defeat the clamp differently than the six we did.
    \item \textbf{The Scope Gate's adversarial test found the opposite result: a real, quantified vulnerability, not a confirmation.} An 11-prompt set of genuinely out-of-taxonomy requirements, each engineered to contain one polysemous incidental keyword (Section~\ref{sec:edge-of-scope}), evaded refusal in $30/30$ attempts across all ten keyword-coincidence prompts (only the no-keyword control was correctly refused), returning confident numeric verdicts for domains the calibration table has no archetype for at all. This is not merely the previously-acknowledged theoretical coarseness of the zero-overlap criterion; it is a demonstrated $100\%$ evasion rate under the exact attack the theoretical concern predicted. Unlike the Entity Grounding and Bounded Projection results above, this asymmetry means the three layers do not currently offer uniform protection: an attacker (or an unlucky choice of words in a legitimate but tangential requirement) is far more likely to defeat the Scope Gate than either of the other two layers.
    \item \textbf{Post-simulation uncertainty annotation fires too often to be a useful decision-support signal on this testbed.} Evaluated against RQ3's own 150 real, live-LLM-parsed cases (Section~\ref{sec:workload-propagation}), it flags $80\%$ of them, almost entirely driven by one node's (\texttt{catalogue\_cpu}) unusually narrow percentile band. This is not the deployment-ready behavior a caveat mechanism needs: a warning attached to four out of five reports gives a user no way to act on it selectively, which is a more serious problem than the mechanism simply being unvalidated. Its per-node P90/P95/P99 thresholds were never intended as calibrated risk boundaries, only as an intuitive default, and this result shows that default does not hold up node-by-node; deployment as a decision-support tool should currently disregard the annotation's caveat rate as a meaningful signal until it is recalibrated, and should instead treat any \textsc{low}- or \textsc{very\_low}-confidence output as at most a prompt to consult the specific flagged node before trusting the number, not as a system-wide risk indicator.
    \item \textbf{Single-intervention scope.} The Parser Agent resolves one $do(X{=}x)$ intervention per requirement; a description that bundles multiple concurrent changes (e.g.\ a new promotion \emph{and} a simultaneous checkout redesign) is not decomposed into a joint or sequential intervention set, and is instead parsed against whichever single archetype the verification layers judge closest. Requirements requiring joint or sequential $do(\cdot)$ reasoning are out of scope for the current implementation.
\end{itemize}

\subsection{A General Specification for Deploying to a New Target System}
\label{sec:general-spec}
Section~\ref{sec:discussion}'s Threats to Validity notes that the Parser Agent's mechanism is now parametrized (system name, domain description, and known-service set are all derived from whichever dependency graph it is constructed with) but empirically validated on Sock Shop alone. We make the remaining onboarding work concrete rather than leave it as an unspecified gap: Table~\ref{tab:general-spec} lists every input a new target system must supply, grouped by how much of it can be automated.

The calibration table itself (\texttt{CALL\_CHAINS}) is, by design, a \emph{per-system artifact}: it is not one fixed table the framework ships with, but one each deployment constructs for its own request taxonomy, in the same way the dependency graph and the gateway set are supplied per system rather than assumed. For Sock Shop we built it by hand from the system's architecture and telemetry log templates (Section~\ref{sec:parser-agent}); the general recipe we recommend instead, and did not use here, is to source archetype descriptions and keywords from the target system's \emph{own} documentation or API specification where one exists, exactly as the corresponding row of Table~\ref{tab:general-spec} states. We flag one gap between this methodology and the current code honestly: the implementation still imports \texttt{CALL\_CHAINS} as a fixed module-level table rather than accepting one as a constructor parameter alongside \texttt{system\_name} and the graph -- so today, pointing the Parser Agent at a second system's dependency graph alone is not sufficient to deploy it there, since the request taxonomy it would consult remains Sock Shop's. Closing this is a small, low-risk refactor (mirroring how \texttt{system\_name} was parametrized), but it does not by itself supply a second system's actual table; that still requires the documentation-driven construction above, which we have not carried out for Train Ticket or any other testbed.

The middle rows are the ones this paper's own construction answers empirically rather than by assertion. The gateway set and \texttt{known\_services} are already computed this way in the current implementation (Section~\ref{sec:parser-agent}), not merely proposed. Archetype candidate services are graph-derivable in principle -- we verified this post hoc on Sock Shop's own graph: enumerating simple paths from the gateway reproduces \texttt{GET\_CATALOGUE}'s and \texttt{PLACE\_ORDER}'s actual service sets exactly -- but a shared node set alone cannot distinguish two archetypes with different customer intent over the same services (e.g.\ \texttt{VIEW\_CART} and \texttt{ADD\_TO\_CART} both touch \texttt{carts}), so path enumeration narrows the candidate space rather than fully determining it. Closing that remaining gap is what motivates the next row: rather than authoring descriptions and keywords from raw log templates as we did here (Section~\ref{sec:parser-agent}), a new deployment should draw on the target system's own documentation or API specification where one exists -- SockShop and Train Ticket, notably, both have one -- since a documented endpoint's own description already resolves the customer-intent ambiguity a bare dependency edge cannot. We did not use this source for the present calibration table and do not claim it here as already validated; it is the concrete next step for constructing one on a second system. The last two rows cannot be shortcut regardless of documentation quality: an archetype's expected workload magnitude is an empirical property of real traffic, not of its specification, and the physical-delta and adjustment bounds are only as trustworthy as the knee-point and adversarial analysis behind them (Sections~\ref{sec:parser-agent}, \ref{sec:discussion}) -- a methodology we have now demonstrated once, and which must be re-run rather than assumed to transfer with the same numbers to a system of different scale.

\subsection{Future Work}
\label{sec:future-work}
Beyond the general specification above, a further direction is validating the interventional Shapley-attribution mechanism (Sections~\ref{sec:background}, \ref{sec:results}) directly rather than assuming its reliability from the mathematical construction alone: a controlled, ground-truth-by-construction protocol -- checking null-condition false-positive rate, dose-response monotonicity, cross-service topology respect, and within-node Tier-1/Tier-2 decomposition, across testbeds of different scale -- is the subject of a companion study \cite{ourxaipaper}. Once its faithfulness is established (and for whichever facets it is not), the natural next step is wiring it into the Capacity Agent's own bottleneck ranking, which currently uses a simpler fixed-threshold heuristic instead. Separately, the post-simulation uncertainty annotation's per-node percentile thresholds (Section~\ref{sec:workload-propagation}) need principled recalibration — likely a robust, outlier-resistant estimator for heavy-tailed nodes like \texttt{catalogue\_cpu} — now that we know the current intuitive default fires on $80\%$ of ordinary cases rather than the rare ones it was meant for. A topology with multiple candidate gateways would let the Entity Grounding layer's fallback be evaluated on the narrower disambiguation task our adversarial set could not construct on Sock Shop, and further adversarial strategies beyond the six we tried against the Bounded Projection's inner clamp would extend confidence in its coverage. Further out, we will explore dynamic graph updates under auto-scaling and an explicit statistical equivalence test (TOST) for the several RQ2 comparisons that fail to reject the null but should not be read as proof of parity.

\section{Conclusion}
\label{sec:conclusion}
We set out to answer a question RCA and observational SCM tooling both leave open: whether an unbuilt requirement is likely to fit within an existing microservice architecture, before it is implemented and before it has any telemetry of its own. Our central contribution is not a claim that a causally-structured model forecasts point values more accurately than a well-tuned regressor — RQ2 shows this is often not the case, and on Train Ticket the SCM wins the fewest head-to-head comparisons of the four models tested. The contribution is a capability regression baselines do not have at all: a bounded, guarded translation from natural-language requirement to $do(X{=}x)$ intervention (RQ3), and a mechanism that can answer the resulting feasibility query by forward simulation through an explicit causal structure, rather than only interpolating within its training distribution. Guards measurably matter — they drove three observed LLM failure modes to exactly zero across repeats where the unguarded baseline's own error varied more than sixfold run-to-run (RQ3) — and so does the SCM machinery underneath them: a single-LLM-call baseline reaches a different feasibility verdict from our guarded, SCM-grounded pipeline on more than half of held-out requirements (RQ5), meaning the causal structure is not merely a costlier route to the same answer.

We report this scope narrowly and on purpose. Accuracy does not transfer uniformly from Sock Shop to the four times larger Train Ticket topology (RQ1, RQ2); the Shapley-based tier attribution this framework's causal structure in principle enables is implemented but not yet validated for faithfulness, so we do not build result claims on it here; and the current implementation covers requirements within a calibrated taxonomy on a single intervention, refusing a numeric verdict rather than guessing outside that boundary (Scope Gate, Section~\ref{sec:scope-gate}). None of these are claims of a superior forecaster. They are the conditions under which a requirement-level, prospective $do(x)$ feasibility query — a question the standard AIOps and regression toolchain has no operator for at all — can be asked and trusted to refuse an answer it is not entitled to give.
